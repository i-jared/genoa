# Production readiness

**Genoa remains beta software with unresolved release gates.** Signup is now open; do not mistake that for production certification. The core flow is implemented, but the remaining reliability and release gates below prevent a public-production sign-off. This review covers Android capture/drafts/upload/playback, API authorization/media/reactions, deletion, live events, jobs, configuration, and release packaging. It is a code review with targeted tests, not a penetration test or a long-duration device certification.

## Findings to address before wider use

### P1 — Make deletion win against in-flight upload completion — addressed September 24, 2026

[Upload completion](../backend/src/media.ts) now publishes with a single conditional batch: the asset row, `ready` state and notification are written only if the message still exists and the author is still a member. Every exit after the R2 object exists and before publication deletes the object, including when a concurrent deletion has already aborted the multipart upload. A five-minute [reconciliation sweep](../backend/src/jobs.ts) removes day-old `media/` objects that belong to deleted or unknown messages or that no table references. `production.test.ts` holds completion open for 1.5 s and for 9 s while the message is deleted and its cleanup job runs. Both cases return 404 and leave neither an asset row nor an R2 object, checked in the local D1/R2 stores. A unit test covers the sweep's keep/remove rules.

### P1 — Make draft discard atomic with worker cancellation — addressed on Android and iOS September 24, 2026 (unreleased)

Discard first writes a `DISCARDED` tombstone to SQLite. It then waits for WorkManager to confirm cancellation and stops the in-process upload with `cancelAndJoin`; the HTTP call is aborted. Only then is local media deleted. Upload writes are conditional and can't change or re-create a tombstoned row. [DraftUploader](../android/app/src/main/java/app/gather/data/DraftUploader.kt) checks the tombstone before setup, before the status request, before each part and before finalization. [DiscardWorker](../android/app/src/main/java/app/gather/data/DiscardWorker.kt) deletes the server message by stable ID with backoff, and is rescheduled after restart or sign-in. The tombstone row is removed only once a DELETE sent at least three minutes after the discard returns 200 or 404, because an early 404 doesn't rule out a request still in flight. A lost final response leaves the draft failed, never sent; discarding it then deletes the message the server already published. `DraftDiscardTest` (10 emulator tests) covers discard during setup, during a part upload, at finalization, after a lost final response, after a simulated restart, an early 404, text drafts, late writes and account isolation. Physical-device soak testing remains. The original finding follows.


[Repository.discard](../android/app/src/main/java/app/gather/data/Repository.kt) requests WorkManager cancellation, then deletes remotely and locally without awaiting cancellation or storing a discard tombstone. [UploadWorker](../android/app/src/main/java/app/gather/data/UploadWorker.kt) writes draft snapshots with an upsert. An in-flight request or late worker write can race the discard; a remote 404 is not proof that a concurrently starting upload cannot subsequently create the message.

Persist a terminal discard state first, make worker updates conditional, and reconcile remote deletion by stable ID. Exercise discard during setup, part transfer, finalization, loss of the final response, and process restart.

### P1 — Bound and recover live capture independently of the screen — mostly addressed on Android and iOS September 24, 2026 (unreleased)

Segment delivery, retry and finishing now belong to the app-lifetime [LiveUplink](../android/app/src/main/java/app/gather/data/LiveUplink.kt) and [LiveEndWorker](../android/app/src/main/java/app/gather/data/LiveEndWorker.kt), not the composable. Segments are recorded in SQLite before upload and sent in order. The queue is capped at 150 segments or 160 MiB. Capture stops cleanly below 300 MiB free space and on errors that retrying can't fix (401/403/404/409/410/413/422, suspension), keeping the replay and showing the reason. A replay save or scheduling failure shows **Try again**. Capture-start errors stay visible, and camera setup errors no longer crash the app. Leaving the screen or the process ending no longer cancels delivery or finishing. Consent: the reply button reads **Go live** and opens preflight, which explains who can watch and starts only on **Start sharing live**. A filled "SHARING LIVE · time" badge is shown, and TalkBack announces it. `LiveUplinkTest` (11 emulator tests) and the end-to-end `GenoaFlowTest` live replay test pass. iOS had the same consent bug: the main camera button started live sharing with no preflight. It also had unbounded fragments and retried every error. Live now always requires **Start sharing live** and shows a LIVE badge. Fragments are capped at 90 or 192 MiB, and stop below 1 GiB free. Terminal errors stop retrying and offer **Stop and save recording**. `finish()` holds a background-task assertion. **Still open:** on Android the camera stops when the screen goes away (no foreground-service capture), and the physical device matrix below has not been run. The original finding follows.


[LiveScreen](../android/app/src/main/java/app/gather/ui/LiveScreen.kt) owns capture, pending segments, and finalization in a composition-scoped coroutine. Its segment channel is unbounded and retries every error indefinitely, including terminal permission errors. A prolonged outage accumulates queued files, while leaving the composition cancels its recovery work. A saved draft exists, but that alone does not prove finalization and delivery survive interruption.

Move durable finalization/retry ownership outside the composable, stop retries for revoked access, bound buffering/disk use, and define low-storage behavior. Test backgrounding, screen lock, fold/unfold, permission revocation, process death, and reconnect during a long capture on two real devices. Also restore unmistakable live consent in preflight: the current camera button is labeled only “Record” although it starts sharing immediately.

### P1 — Revoke every live subscription when deleting an account — addressed September 24, 2026

[Account deletion](../backend/src/account.ts) collects every membership before deleting and revokes the sockets in all of those rooms. Suspension does the same. [ConversationRoom](../backend/src/realtime.ts) now also rechecks current membership (and suspension) on every broadcast and closes sockets that no longer qualify, so a missed revoke can't leak hints. It also stopped echoing the invalid close code 1005. Tests confirm that a non-owner member's socket closes with 1008 when they delete their account, and that a suspended person's socket closes too.

### P2 — Persist watch progress while offline — addressed in 0.2.8

The original review found progress sent without durable retry. The 0.2.8 follow-up adds account-scoped SQLite progress, coalesced retry, monotonic completion, revision-specific acknowledgments, and service-owned background progress. Offline failure/store-reopen/reconnect and stale-response tests cover this correction; see [current verification](FEATURES.md). Physical-device weak-network soak testing remains a release gate.

### P2 — Enforce media and resource limits beyond file extensions — server side addressed September 24, 2026

Android imports now check the declared size against 8 GiB and free space before copying. Video and audio must be H.264/HEVC or AAC and between 0 and 24 hours long; photos are checked for image dimensions. The copy aborts past 8 GiB or when free space would drop below 512 MiB, and the partial file is deleted. Server `storage_quota` and `unsupported_media` rejections are final: the draft shows the server's message with **Retry upload** and **Discard** (`MediaImportTest`, `DeliveryRulesTest`).

Server side: publication now walks the MP4 box structure with block-cached range reads (at most a few R2 reads for typical files; [mp4.ts](../backend/src/mp4.ts)). It requires a timed H.264/HEVC video track for video or an AAC-only track for voice, and rejects anything else with a terminal `422 unsupported_media`. JSON bodies are capped at 64 KiB (diagnostics 256 KiB). Reactions are capped at 200 per person per message, and responses list the latest 500. Each account has a storage quota (default 25 GiB, counting uploads in progress) returning `413 storage_quota`. Tests cover real moov-first, moov-last and fragmented files, fake `ftyp` headers, truncation, unknown codecs, the quota, the body cap and the reaction cap. Dimensions are not checked. Live segments are not counted toward the quota. The original finding follows.

[Media publication](../backend/src/media.ts) checks a few magic bytes, size, and declared MIME, not decodability. [Import](../android/app/src/main/java/app/gather/data/Repository.kt) copies a whole provider stream before checking usable metadata and has no local byte cap. Malformed or incompatible files can reach publication or exhaust phone storage. Reaction arrays and some account/history aggregates are also unbounded, and there is no aggregate per-account storage quota.

Validate supported codecs/dimensions/duration before publication, fail unsupported imports clearly, enforce streaming byte limits, bound JSON and reaction responses, and introduce measurable account/storage limits. Do not advertise arbitrary video imports until this is verified.

## Release and operating gates

- **Release signing:** [Android build configuration](../android/app/build.gradle.kts) now supports environment-based production signing. The earlier beta uses the development key. The `app.genoa` APK and AAB are signed with the newly authorized upload key; back up its private material and enroll in Play App Signing. Apple team/bundle provisioning and cloud-managed App Store signing/export are complete; the final IPA signature and production push entitlement are verified. See [the release handoff](../store/README.md).
- **Account recovery:** implemented. [Authentication](../backend/src/auth.ts) sends password-reset and email-confirmation emails through Resend. Reset links open a script-free Worker page, work once, expire in an hour and revoke other sessions. Unknown emails get the same response, and email is sent after the response so timing doesn't reveal accounts. Requests are limited to five per minute per IP. New passwords need eight characters. Tested end to end locally with the development mail table. Still to do: configure `RESEND_API_KEY`/`EMAIL_FROM` with a verified sending domain, and confirm delivery and the reset page on production.
- **Moderation:** implemented. The admin console (`admin/`, Next.js on Vercel) and Worker `/admin/*` API cover the report queue, message removal, suspension, user search, diagnostics and an audit log. Suspension blocks sign-in and every API call. Reports now require access to the reported message. Still to do: deploy the console, grant the first admins, and staff the 24-hour review commitment. Admin accounts use password-only sign-in with no second factor.
- **Operations:** dead-lettered jobs are recorded and can be retried or discarded from the console. The cron alerts (log line, plus email when `ALERT_EMAIL` is set) on failed jobs, reports older than 24 hours and outbox backlog. `scripts/ops/restore-drill.sh` exports D1, restores it into a scratch database and compares every table. It was rehearsed locally (35 tables matched) but **has not been run against production**. R2 media has no point-in-time backup. Cloudflare dashboard notifications (error rate, billing, storage) are still to be configured. See [operations](OPERATIONS.md).
- **Repeatable releases:** `.github/workflows/ci.yml` runs the backend suites against a local Worker, the admin build/tests, Android unit tests/lint/builds and iOS simulator unit tests. The repository has no Git remote yet, so the workflow has never run. Deployment and release signing remain manual.
- **Device/accessibility evidence:** verify two-device send/watch/reply, long recordings, weak-network restart/retry, interruptions, large text, TalkBack, and an optimized signed build. Emulator screenshots alone cannot establish camera, battery, or background behavior.

## Live error recovery

The September 21 source review also found that `LiveScreen.finishWithReplay` can fail while saving or scheduling upload without exposing a handled recovery state, and capture-start errors may disappear when the screen closes. Preserve recoverable files, make finalization retryable outside the screen, and keep failures visible with a deliberate recovery action. These findings were not reproduced through physical-device fault injection and remain unverified as fixed.

Prior build/emulator evidence and current selection behavior are consolidated in [FEATURES.md](FEATURES.md). Historical findings above are retained until explicitly reproduced or resolved; repository cleanup is not a fresh security review.
